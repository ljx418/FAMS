# 全量 E2E 运行时加固开发及验收计划

日期：2026-10-08

## 1. 问题与目标

最新一次全量验收暴露了两个不能接受的假绿风险：真实数据 E2E 在后端启动前执行，以及浏览器截图路径没有把 HTTP 5xx 计入失败。同时，普通读取持仓轮动页面会重写 `RelativeRotationPoint`，快速跨页时可能触发 SQLite 事务争用。

本子阶段只修复验收编排和只读边界，不改变策略公式、账户事实或交易权限。

## 2. 实施范围

1. 将依赖 HTTP 的每日复盘真实数据 E2E 移到后端健康检查之后执行。
2. `getHoldingsRotation` 只读路径禁止持久化 RRG 计算点；显式刷新和回测路径保持原有写入合同。
3. Headless Chrome 捕获所有 HTTP 5xx，并将其作为浏览器验收失败。
4. 三视口基线改为逐页面独立浏览器生命周期，避免前一页面请求污染后一页面。
5. 增加只读持久化不变性验收，并重新运行全量 E2E。

## 3. 自动验收门槛

- 无预启动服务时，全量脚本能够自行启动后端和前端。
- `daily review real data` 必须在后端健康后执行并通过。
- 连续读取持仓轮动数据前后，`RelativeRotationPoint` 数量和摘要不变。
- 浏览器报告必须同时满足截图步骤通过、控制台无错误、HTTP 5xx 数量为 0。
- 1440、768、390 三个视口的八个基线页面互相隔离。
- 后端 TypeScript、前端构建、轮动缓存合同及全量 E2E 通过。
- 自动范围必须为 `passed`；完整 PRD 只能因集中人工质量门保持 `blocked`。
- 四个交易锁继续为 `false`。

## 4. 防假绿约束

- 不允许通过预先常驻后端掩盖验收脚本的启动顺序错误。
- 不允许截图成功但后台接口 5xx 时判定浏览器通过。
- 不允许普通 GET 为生成可读页面而修改策略点或账户事实。
- 不允许把集中人工核查改写为自动通过。
